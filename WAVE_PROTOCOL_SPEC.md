# Wave Protocol / Wave Baskets — Product and Implementation Spec

Status: Draft for issue publication. Testing approach confirmed by the user. Publication requires project issue-tracker configuration; intended triage label: `ready-for-agent`.

Source: the supplied “Wave Protocol / Wave Baskets: ETHGlobal Mumbai Build Plan (Uniswap + Chainlink CRE + Anon-RPC).” This spec synthesizes that document; its operational instructions are not actions authorized or performed by this conversion. External claims, dependency versions, deployment addresses, deadlines, and prize rules have not been independently reverified.

## Problem Statement

Testnet users need a simple way to create and hold a diversified token basket, understand the value of its underlying assets, and exit either into a settlement token or the assets themselves. A basket should enforce its allocation rules, disclose fees, and remain redeemable in kind when swap liquidity or price feeds are unavailable.

Creators need bounded allocation management and transparent profit-based compensation. Holders need visibility into rebalances and the relationship between underlying net asset value (NAV) and secondary-market share prices. Users also need to understand which application reads use Anon-RPC and when a direct connection would expose their network information.

## Solution

Build a Sepolia-only Wave Protocol demo in which users create ERC-20 share-token baskets, deposit mock USDC, and receive shares backed by mock WETH, WBTC, LINK, and any supported settlement-token allocation. Uniswap v4 executes asset purchases and sales. Chainlink feeds provide valuation, and a Chainlink CRE workflow combines on-chain holdings with an external market-data API to propose bounded rebalances.

The flagship basket starts with 40% WETH, 35% WBTC, and 25% LINK. Its FUND/mUSDC secondary-market pool uses NavGuardHook to charge fees according to price deviation from oracle-derived NAV and swap direction. A browser dashboard supports creation, holdings, deposits, both redemption modes, fees, history, and privacy inspection. Application RPC reads use Anon-RPC by default, with visible startup state, traffic accounting, and an explicit opt-in for any direct fallback.

## User Stories

2. As a visitor, I want to see the active network and mock-asset labels, so that I understand this is a testnet demo.
3. As a participant, I want to connect a supported wallet and switch to Sepolia, so that I can transact on the correct chain.
4. As a participant, I want a rate-limited mock-token faucet, so that I can try the product without acquiring real assets.
5. As a creator, I want to name my basket and share token, so that users can identify it.
6. As a creator, I want to choose up to four allowlisted assets, so that my basket has a supported composition.
7. As a creator, I want weights totaling 10,000 basis points with no asset above 5,000 basis points, so that allocation rules are explicit and enforced.
8. As a creator, I want invalid, duplicate, or unsupported assets rejected, so that my basket cannot have an ambiguous composition.
9. As a creator, I want to provide seed capital when creating a basket, so that it starts with funded shares and inflation protection.
10. As a creator, I want to set a disclosed performance fee, so that compensation is visible before users deposit.
11. As a participant, I want new baskets to appear in the factory listing, so that I can find user-created baskets.
12. As a depositor, I want to approve and deposit mUSDC, so that I can acquire a basket in one deposit transaction.
13. As a depositor, I want purchases to follow target weights through Uniswap v4, so that my deposit acquires the basket's underlying assets.
14. As a depositor, I want shares based on the measured value actually added, so that transfer discrepancies and swap execution are reflected in my allocation.
15. As a depositor, I want a minimum-shares constraint, so that an unfavorable deposit reverts.
16. As a holder, I want current NAV and NAV per share, so that I can understand the value backing my position.
17. As a holder, I want token balances, actual weights, and target weights, so that I can see composition and allocation drift.
18. As a holder, I want an explicit oracle-health indicator, so that stale or invalid valuation is visible.
19. As a holder, I want to redeem some or all shares into mUSDC with a minimum output, so that I can exit with bounded execution risk.
20. As a holder, I want to redeem my proportional underlying assets without swaps, so that I can exit when liquidity is unavailable.
21. As a holder, I want in-kind redemption to remain available during an oracle outage, so that missing prices do not trap my assets.
22. As a holder, I want withdrawal fees and recipient information disclosed, so that I understand the cost of exiting.
23. As a holder, I want performance fees charged only on gains above a fund-level high-water mark, so that previously charged gains are not charged again.
24. As a holder, I want fee dilution and the high-water mark visible, so that I can understand creator compensation.
25. As a creator, I want to propose new weights through a timelock, so that holders can observe a pending allocation change.
26. As a participant, I want proposed weights and their execution time visible, so that I can distinguish pending and active allocations.
27. As a holder, I want automated rebalances bounded by allowlists, weights, turnover, execution interval, and slippage, so that an external strategy cannot bypass vault rules.
28. As a demo operator, I want CRE to read holdings and external market data, so that automated allocation changes have meaningful external input.
29. As a demo operator, I want a deterministic strategy without an LLM dependency, so that the core workflow remains demonstrable when an LLM is unavailable.
30. As a holder, I want insignificant drift to skip execution, so that unnecessary trades are avoided.
31. As a holder, I want rebalance history with allocation changes, turnover, NAV impact, and a reason reference, so that I can inspect automated decisions.
32. As a holder, I want unauthorized, stale, replayed, or unknown-vault rebalance reports rejected, so that reports cannot bypass execution controls.
33. As a trader, I want to swap flagship FUND shares against mUSDC, so that I can demonstrate secondary-market trading.
34. As a trader, I want lower fees for swaps toward NAV and higher fees for swaps away from NAV outside the configured band, so that the pool rewards price convergence.
35. As a trader, I want hook swaps rejected when NAV is unhealthy, so that invalid valuation does not drive fee decisions.
36. As a participant, I want transaction progress, errors, confirmations, and explorer links, so that I can tell whether an action succeeded.
37. As a holder, I want a portfolio of my basket positions, so that I can inspect balances and available exits.
38. As a privacy-conscious visitor, I want application reads routed through Anon-RPC by default, so that ordinary dashboard use follows the declared privacy policy.
39. As a visitor, I want visible worker startup and failure states, so that I know when private reads are ready.
40. As a visitor, I want direct fallback to require an explicit click for a single read, so that worker failure never silently changes my privacy choice.
41. As a visitor, I want traffic counts by route and JSON-RPC method, so that I can inspect how much application traffic used Anon-RPC.
42. As a visitor, I want bootstrap, wallet, and off-browser CRE exceptions explained, so that I understand the limits of the privacy claim.
43. As a visitor, I want reads cached and batched, so that privacy routing does not make the dashboard unnecessarily slow.
44. As a demo operator, I want reproducible deployment configuration and recorded transaction hashes, so that I can verify the full integration.
45. As a reviewer, I want documented contracts, integration evidence, limitations, and attribution, so that I can reproduce and evaluate the demo.

## Implementation Decisions

- **Repository baseline and terminology.** The workspace is empty: no implementation, test suite, project glossary, ADRs, Git remote, or issue-tracker configuration was found. Use the source vocabulary: basket, vault, creator, holder, target weights, actual weights, NAV, NAV per share, high-water mark, rebalance, and protocol treasury. A basket is represented by one vault and its ERC-20 shares; FUND is the flagship basket's share token.
- **Architecture.** Build three components: Foundry-based contracts, a TypeScript CRE workflow, and a Vite/React/TypeScript static dashboard. Use Sepolia, chain ID 11155111. No backend, database, indexer, or upgradeable proxy is required. The factory deploys independent vaults directly.
- **Dependency baseline.** Start with Solidity 0.8.26 targeting Cancun, the Uniswap v4 template and its compatible core/periphery dependencies, OpenZeppelin 5.x, and the CRE TypeScript SDK with Bun. The source proposes React 19, wagmi 2.19.x, viem 2.x, RainbowKit 2.2.11, TanStack Query 5, and Anon-RPC browser harness 0.3.2. Resolve compatibility and pin exact versions during setup; conflicting or tentative “latest” claims in the plan are not final pins.
- **AssetRegistry.** Maintain the token allowlist, token and feed decimal information, feed address, maximum staleness, and acceptable answer bounds. Read and normalize prices consistently. Reject nonpositive, out-of-bounds, stale, incomplete, or invalid-timestamp rounds. Check actual feed responses during deployment. Treat supported assets as mock representations, not redeemable claims on real assets.
- **Valuation units.** mUSDC uses six decimals, mWETH and mLINK eighteen, mWBTC eight, share tokens eighteen, and normalized USD prices eighteen. NAV is exposed in settlement-token units; NAV per share has an explicitly documented eighteen-decimal convention. Account for mUSDC/USD rather than silently assuming a fixed dollar peg. Normalize pool prices for currency order and token decimals.
- **WaveFactory.** Create funded vaults with name, symbol, asset list, target weights, creator performance fee, and seed amount. Reject mismatched arrays, duplicates, unsupported assets, zero addresses, more than four assets, weights exceeding 5,000 bps, and totals other than 10,000 bps. Register and enumerate created vaults and emit creation events. Zero-weight handling and performance-fee bounds must be fixed before implementation.
- **WaveVault public interface.** Support deposit with input amount, minimum shares, and recipient; redemption with shares, minimum settlement output, and recipient; in-kind redemption with shares and recipient; holdings and valuation reads; pending-weight proposal and execution; authorized rebalance; fee crystallization; and indexed rebalance-history reads. Reject invalid recipients and zero-value operations. Emit observable events for user actions, fees, proposals, and rebalances.
- **Deposit accounting.** Crystallize any outstanding performance fee before a new depositor participates in existing gains. Measure settlement tokens actually received, purchase assets at target weights, and value actual underlying balance changes using healthy feeds. Mint shares from value added relative to pre-deposit NAV and supply, with rounding favoring the existing vault. Enforce the user's minimum shares and bounded execution loss. Handle any settlement-token component without attempting a token-to-itself swap.
- **Bootstrap and inflation protection.** Require a creator seed, with 10 mUSDC and 1,000 permanently locked share units proposed in the plan. Define the initial share-price scale explicitly, deduct locked shares from the creator's seed entitlement, and test donation/inflation attacks. Never apply the ordinary supply/NAV ratio to an uninitialized vault.
- **Settlement-token redemption.** Crystallize fees, calculate and burn the holder's proportional shares, sell the corresponding underlying assets, enforce oracle-derived swap minimums and the user's net minimum output, and transfer the withdrawal fee to the treasury. A nominal 10 bps withdrawal fee is proposed, subject to the final fee configuration below.
- **In-kind redemption.** Transfer proportional raw token balances without swaps or price reads. Preserve this exit during oracle and liquidity failures. The source's proposed fee-in-shares model must use supply-based accounting; it must not require a fresh valuation or block exit while trying to crystallize performance fees. Final ordering and deferred fee treatment are an implementation gate.
- **Performance fees.** Use a fund-level NAV-per-share high-water mark. Charge only gains above the mark, mint dilution-adjusted fee shares to the creator, and update the mark to post-fee NAV per share. Include decimal and basis-point scaling. Deposits and withdrawals must not create feeable gains. Explain the limitations of a fund-level mark; per-investor equalization is outside this demo.
- **Manual weight changes.** Only the creator proposes weights; execution becomes permissionless after the proposed ten-minute demo timelock. Revalidate allocation rules at execution. Make the pending weights and ETA readable. Separate activation of a target allocation from the bounded trading operation; proposal replacement, cancellation, and coordination with CRE require explicit semantics before implementation.
- **WaveSwapAdapter.** Expose exact-input, single-hop swaps with token pair, amount, minimum output, and recipient through one adapter boundary. Use the v4 PoolManager unlock/swap/settle/take flow. Authenticate callbacks, bind them to the active operation, and prevent arbitrary caller access to vault funds. Deploy and seed three underlying-asset/mUSDC pools at normalized oracle prices. The proposed pool fee is 3,000 v4 fee units with tick spacing 60. Any test-router fallback remains a disclosed demo-only choice.
- **NavGuardHook.** Restrict callbacks to PoolManager and initialization/swaps to registered pool keys. Only the flagship FUND/mUSDC pool receives this hook. Register the pool before initialization; create it with the dynamic-fee flag and return the fee override flag on every permitted swap. Mine a deployment address matching the enabled hook permissions. Reject unhealthy NAV.
- **Hook pricing.** Use pool spot only to measure deviation and trade direction; derive the reference NAV from the vault's underlying holdings and feeds, never from that pool's spot price. The plan proposes 0.05% toward NAV and 1% away beyond a 1% band. Exact fee tiers, inside-band behavior, and crossing-NAV behavior remain configuration decisions, with explicit boundary tests required.
- **CRE workflow.** Use a cron trigger, inspect the factory and vault holdings, obtain external market data, compute deterministic proposed weights, constrain and normalize them, and skip allocations below the drift threshold. Proposed settings are a ten-minute cadence, 300 bps drift threshold, and at most three baskets per run. Ensure deterministic input validation and aggregation. An optional LLM may suggest numeric weights but cannot replace mandatory external-data use or on-chain bounds.
- **WaveRebalanceReceiver.** Accept a report containing vault address, target weights, observation timestamp, and reason hash. Authenticate the configured forwarder and expected workflow metadata, confirm factory membership, reject future/stale timestamps and replay, and invoke the authorized vault rebalance path. The source proposes a fifteen-minute freshness window. Define timestamp/report ordering so a failed execution can be retried while an accepted report cannot be reused.
- **On-chain rebalance bounds.** Independently enforce allowlists, asset count, 5,000 bps maximum weight, 10,000 bps total, 2,000 bps maximum turnover, a minimum execution interval proposed at five minutes, healthy prices, per-swap minimum output, and a post-swap NAV-loss bound. Do not trust workflow-side clipping as enforcement. Cap receiver-provided slippage by a vault-level limit. Define turnover and drift against actual holdings consistently before implementation.
- **CRE demonstration.** A successful baseline demonstration uses simulation with broadcast enabled, a nonzero transaction hash addressed to the configured simulation forwarder, and an observed vault rebalance. Repeating the workflow immediately must produce no second rebalance, whether skipped for drift or the interval guard. A dry run or manual transaction is disclosed fallback evidence and does not satisfy this full integration acceptance criterion.
- **Forwarder trust.** Restrict the mock forwarder to disposable testnet demonstrations and disclose that mock-forwarder authentication does not establish production authenticity. Keep all vault bounds active. Production-forwarder migration requires a separate validated deployment; changing one address alone is not production readiness.
- **History.** Keep the most recent 32 rebalance records on-chain, with monotonically increasing IDs and events for older history. Records contain old/new weights, NAV before/after, turnover, and reason hash. Read recent records first; query older events from the deployment block in bounded, provider-adaptive chunks, initially up to 5,000 blocks. Specify expired-ID behavior explicitly.
- **Dashboard surfaces.** Provide basket discovery, basket creation, basket details, portfolio, faucet, and privacy views. Basket details include holdings, actual/target/pending weights, NAV health, balances, fees, high-water mark, deposit, both redemptions, and rebalance history. Show token approvals and transaction states accurately. Charts are optional; usable tables are sufficient. Hook trading may be demonstrated by script rather than a dedicated trading UI.
- **Anon-RPC transport.** Initialize one worker per page and use its fetch transport for every app-originated JSON-RPC read, including contract calls, balances, chain checks, block numbers, receipts, and logs. Keep application reads separate from wallet signing/broadcast. The plan's immutable Nox worker is the initial candidate; validate its specifier, harness interface, sandbox setup, and browser behavior during the dependency spike.
- **Privacy failure behavior.** During startup, show a booting state; on failure, preserve the private-read policy. After a proposed sixty-second timeout, offer an explicit single-read direct action. Count the action and turn the privacy badge amber. Never introduce automatic direct fallback through retry, another client, or a wallet provider.
- **Traffic accounting.** Count JSON-RPC method calls, including individual members of a batch, by anon, bootstrap, and explicit-direct route. Display errors/retries separately so failures cannot inflate a success claim. Report successful-call privacy coverage as anon divided by anon + bootstrap + explicit-direct successes; show attempted counts as well. Wallet and CRE traffic are outside browser-meter coverage and must be disclosed separately.
- **Performance acceptance.** Target cold worker startup under ten seconds on the demo network and at least 95% successful anon coverage across the recorded lifecycle, with zero explicit-direct calls. Bootstrap reads remain visible in the denominator. Batch compatible reads and use a proposed fifteen-second query-cache freshness period. Record observed results instead of presenting targets as achieved guarantees.
- **Deployment and delivery.** Use a single chain-specific deployment manifest for contract addresses, tokens, pools, feeds, forwarder, worker configuration, and deployment block; share it with dashboard and workflow. Validate dependencies before deployment, seed demo liquidity, verify contracts where supported, and record transaction hashes. Keep deployer credentials in a keystore, workflow secrets outside version control, and secret-bearing configuration out of frontend bundles.
- **Scope priority.** Preserve factory creation, deposit/NAV, both exits, fee behavior, bounded CRE integration, hook behavior, and privacy metering. Optional cuts are the LLM, Nym selector, charts, creation-flow polish, multi-basket workflow iteration, and hook-pool UI. The full baseline includes the deployed hook; a hook shown only in tests is a partial delivery and must be labeled accordingly.

## Testing Decisions

- **Confirmed primary seam.** The user approved one primary integration boundary: the publicly observable basket lifecycle, from factory creation through deposit, CRE rebalance, flagship hook swaps, and both exits. Prefer this integrated fixture and reusable setup over adding test-only production interfaces. Targeted tests supplement it for accounting, access control, hook fees, and browser privacy failures.
- **What makes a good test.** Assert balances, share supply, fees, allocation outcomes, public events, transaction success/rejection, visible UI state, and observable network routing. Do not assert private helper calls, internal layout, implementation snapshots, or exact SDK call sequences. Use deterministic prices/liquidity and explicit rounding tolerances to isolate economic behavior.
- **Prior art.** No existing tests or test seams exist in this workspace. Adopt the compatible Foundry/v4 template harness when scaffolding. Keep local deterministic contract tests, a pinned Sepolia fork integration run, and a browser lifecycle run distinct so external outages do not masquerade as accounting failures.
- **Factory and registry.** Cover valid creation, registration, independent vault state, asset count, duplicate assets, invalid weights/fees, seed minimums, decimal normalization, stale and invalid feed rounds, bounds, and explicitly labeled mock-feed mode.
- **Vault accounting and fees.** Cover actual received value, partial fills or transfer discrepancies where supported, minimum shares, partial/full exits, recipient handling, withdrawal-fee routing, creator dilution, no fees below the mark, no repeated fee on the same gain, and pending fees before a new deposit. Exercise initial supply, rounding, donations, inflation attempts, and malicious token callbacks through public operations.
- **In-kind availability.** With stale, reverting, or otherwise unusable feeds and with zero pool liquidity, prove proportional underlying transfers and the configured fee treatment still succeed. Confirm no price-dependent fee path can block the exit. Allow only documented token-unit rounding dust.
- **Swap and hook behavior.** Exercise actual PoolManager settlement, input/output ordering, token decimals, enforced output minimums, skewed/thin liquidity, unauthorized callbacks, unregistered pool rejection, required dynamic-fee behavior, direction-sensitive tiers, boundary/crossing trades, and unhealthy NAV. Use the template's test deployment mechanism for hook address flags; test the actual mined deployment on Sepolia.
- **Rebalance and receiver behavior.** Test unauthorized sender/workflow, unknown vault, malformed payload, future/stale/replayed reports, interval violations, invalid allocations, excessive turnover, excessive slippage, unhealthy feeds, and post-trade NAV loss. Assert a rejected rebalance leaves balances, targets, history, and fee state unchanged. Test valid report acceptance through the forwarder boundary.
- **Workflow behavior.** Supply controlled chain and external HTTP inputs and verify bounded outputs, invalid-data handling, drift-based skips, and unavailable-LLM behavior. Demonstrate a real broadcast simulation and correlate its transaction with the vault event and dashboard history. Repeating an unchanged run must not cause another trade.
- **Fuzz and invariants.** Check accepted target weights sum to 10,000 and obey caps; exits cannot exceed entitled assets; share/accounting changes follow the selected rounding rules; and balances reconcile after sequences of deposits, fees, rebalances, donations, and exits. Verify deposit/redemption NAV-per-share preservation only under fixed prices and after accounting for explicit fees, realized slippage, and rounding. Do not use the source's unconditional positive-supply-implies-positive-NAV assertion: locked shares, dust, and asset losses require qualified invariants.
- **Browser privacy.** Intercept outbound requests during cold boot and normal use. Verify all application read clients use the anon transport, bootstrap exceptions are counted, no silent fallback occurs on timeout/retry, a single direct opt-in cannot authorize later reads, the badge changes, batch counts reconcile, and wallet traffic is disclosed. Exercise the actual harness in a real browser as well as deterministic failure controls.
- **History and UI.** Cover fewer than and more than 32 rebalances, expired record IDs, event pagination/provider-limit responses, empty portfolio, rejected transactions, stale feeds, and disconnected/wrong-network wallets. Verify chain-confirmed state updates instead of optimistic success messages.
- **Sepolia release acceptance.** Obtain faucet funds; create a basket; deposit 1,000 mUSDC under controlled liquidity; reconcile dashboard NAV to the public contract read; broadcast a CRE rebalance; observe its history entry; execute flagship hook swaps in both directions; redeem half to mUSDC and the rest in kind; inspect traffic totals; and reload cold. Record addresses, transaction hashes, oracle mode, boot time, and coverage. Target deposit holdings within one percentage point of configured weights and settlement redemption of at least 99% of oracle-valued entitlement less the disclosed fee under the seeded demo conditions. These are fixture-specific thresholds, not return guarantees. Run the completed lifecycle twice from reproducible conditions before release.

## Out of Scope

- Mainnet, real deposits, production investment management, audits, and claims of financial return.
- CCIP, cross-chain state changes, additional chains, RWA, DAO governance, yield aggregation, marketplaces, and backtesting.
- Backend services, databases, indexers/subgraphs, server rendering, Docker agents, and Go/Python application services.
- Upgradeable vaults, arbitrary strategies, arbitrary token support, and automatic hooked pools for every basket.
- Per-investor performance-fee equalization, guaranteed secondary-market prices, and guaranteed liquidity.
- Mandatory LLM use, Nym support, Tor-default transport, elaborate charts, and dedicated hook-trading UI.
- Routing wallet-provider or off-browser CRE traffic through the browser worker, or claiming complete network anonymity.
- Executing the source's deployment, push, form submission, video recording, or hackathon submission instructions as part of this spec conversion.
