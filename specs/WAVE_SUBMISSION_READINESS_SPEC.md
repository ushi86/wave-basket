# Wave Protocol — Submission Readiness and Contract Hardening

Status: Specification draft, saved locally; issue publication pending tracker setup. The user confirmed the existing testing boundaries and added the mandatory negative-test and evidence-validation conditions incorporated below.

Source: the supplied Wave Protocol engineering brief, the current repository, and this conversation. Commands, deadlines, and operational instructions in the attachment are requirements to specify, not actions performed by this conversion. This spec supplements the original Wave Protocol product spec. It does not authorize account creation, service registration, login, deployments, pushes, form submission, or event submission merely because those actions appear in the source.

Implementation steering from the user: for this submission, do not implement a deferred reserve. Crystallize fees before healthy-feed in-kind exits if independently testable. Stale-feed in-kind exits must remain immediate, full and pro-rata after the existing withdrawal fee, with no withheld assets; disclose that they can avoid uncrystallized creator fees. The stale-fee conservation change remains blocked, and any future reserve must have an enforceable expiry. These instructions supersede the unconditional stale-fee conservation requirements below.

## Problem Statement

Wave Protocol has a working local demonstration, but the team cannot yet substantiate a complete hackathon submission with a public repository, verified Sepolia lifecycle transactions, an actual CRE CLI broadcast, and full-session Anon-RPC measurements. Existing local transactions, mock components, compiler outputs, and worker-only probes establish narrower facts and must not be promoted into evidence for the missing integrations.

The current implementation also has intentional limitations that the new brief asks to change: choosing in-kind redemption can avoid outstanding creator performance fees; the receiver has timestamp/hash replay protection without an explicit report nonce; and the hook accepts owner-registered pool keys rather than restricting use to exactly one approved flagship key. These changes must preserve exits during oracle outages, existing safety bounds, private-read failure behavior, and already working user flows.

The team needs an honest, reproducible readiness assessment and an explicit separation between submission work, user-controlled prerequisites, and post-event production hardening.

## Solution

Deliver a submission-readiness increment around the existing basket lifecycle. First establish eligibility and a reproducible baseline, then address the required contract changes with regression tests, deploy and exercise the intended integrations on canonical Sepolia, collect genuine CRE CLI and browser privacy evidence, and prepare reviewable documentation and user-led submission materials.

Maintain a claim-evidence matrix with explicit Proven, Partial, Not done, and Mock-only statuses. Provide a read-only submission-evidence validator that fails when required evidence is missing, malformed, inaccessible, inconsistent, or from the wrong environment. It must never invent, create, or rewrite evidence to make a check pass.

Keep Phase A as the pre-submission scope. Capture Phase B as a gated post-event backlog, with professional review required before any production-readiness claim.

## Implementation Decisions

- **Scope and precedence.** This increment changes the existing implementation only where this spec explicitly requires it. Preserve the original public basket lifecycle and the fixes already verified in review: post-fee settlement previews, exact hook-band boundaries, public pending allocations, history details, treasury disclosures, and private-read failure behavior. The user's testing and evidence conditions are mandatory. Other operational details in the attachment are requirements for future execution, not completed actions.
- **Current baseline.** The repository contains a factory with a dedicated vault deployer, registry, swap adapter, vault, hook, receiver, CRE workflow, and React/viem dashboard. Previous verification reports 20 Foundry tests and five TypeScript tests, successful builds, local lifecycle checks, and a real worker-only Sepolia probe. These are historical observations; rerun and timestamp them during Phase A rather than asserting they were rerun while writing this spec. No configured public remote or issue tracker was found.
- **Eligibility gate — A0.** Record genuine commit dates and obtain the official kickoff timestamp and applicable rules from the project owner and authoritative event material during implementation. Current history contains a large implementation commit; disclose it instead of claiming that no such commit exists. Commit shape alone does not establish ineligibility. If pre-kickoff code or another eligibility conflict is established, pause eligibility-dependent publication/submission work for the owner's track/disclosure decision. Preserve local evidence and do not rewrite, squash, or backdate history.
- **Claim-evidence model — A0/A8.** Maintain the requested EVIDENCE.md matrix with the columns Claim, Status, Evidence link, and Date/time IST. Status is exactly Proven, Partial, Not done, or Mock-only. Keep environment, chain, release commit, component mock flags, command/result, and blocker context in the linked evidence record. Enumerate every README claim at an appropriate level of specificity. A result can prove only the fact it directly demonstrates; a WASM build does not prove CLI execution, and a worker probe does not prove full-session privacy coverage.
- **Public repository — A1.** After the owner supplies or creates the intended public repository and completes any login, publish the preserved history without force-pushing or rewriting it. Verify unauthenticated public access and the submitted commit. Check the MIT license for project-owned source and preserve upstream licenses. Record the URL and actual publication result; never infer success from a configured remote alone.
- **Naming — A2.** Search application source, ABIs, metadata, scripts, and documentation for obsolete Harbour/Harbor branding. Rename remaining product references deliberately, preserving quoted historical provenance where identified as such. Do not alter deployed storage layouts or contract compatibility merely to change labels. Record the checked exclusions and test results.
- **Healthy-oracle in-kind fees — A3.** Replace the current intentional performance-fee waiver with crystallization before calculating the in-kind pro-rata payout when feeds are healthy. Use the same fund-level high-water mark, fee calculation, dilution, and rounding conventions as the settlement exit. Update previews, events, fee-share totals, and UI/documentation together. Compare creator economic entitlement across paths at the same valuation, controlling separately for withdrawal-fee denomination, swap costs, and token-unit rounding.
- **Stale-oracle exit and fee conservation — A3 design gate.** In-kind redemption must remain available without successful price reads. Preserve the departing holder's outstanding fee obligation through an explicitly accounted, backed or enforceable deferred claim; a ledger entry with no collection source is insufficient. Do not forgive the fee by choosing another exit path or charge it to later/remaining holders. Specify the stale-period valuation basis, liability units, attribution, settlement trigger, collection source, rounding, and release behavior before implementing this change. A candidate reserve or claim mechanism must be reviewed against the nonblocking exit requirement; this spec does not invent a fee rate, reserve percentage, historical price, or settlement deadline. If no design satisfies both constraints, report A3 as unresolved and retain/disclose the existing behavior rather than marking the requirement complete.
- **Single approved hook key — A3.** Bind the deployed hook to exactly the approved flagship PoolKey, including both ordered currencies, fee flag, tick spacing, and hook address. Register/configure it before initialization and reject all other keys, including keys with the same currencies but different parameters. Retain PoolManager authentication for all callbacks, dynamic-fee pool creation, override flags, fees bounded to 500–10,000 v4 units, and precise band comparisons. Retain the existing fail-closed unhealthy-NAV behavior unless an explicitly documented, tested change is required; in-kind exits remain independent of hook availability.
- **Report schema and ordering — A3/A5.** Extend reports with an explicit per-vault nonce and observation time while preserving target weights and the reason reference. Use one matching encoding across workflow, receiver, tests, and configuration. Reject unknown vaults, invalid metadata where applicable, stale/future observations, previously accepted nonces, and replayed payloads. Define monotonic nonce ordering and update it only with successful accepted execution; a reverting execution must roll back consumption. Keep freshness configurable within a documented safe policy, preserving the current fifteen-minute ceiling unless an independently justified requirement changes it. Never increase a window to make stale evidence pass.
- **Deployment compatibility.** Existing contracts are ordinary immutable deployments, not upgradeable proxies. Receiver payload changes and vault accounting changes require an explicit new deployment/configuration transition; do not assume old and new reports or addresses are interchangeable. Preserve ABI alignment, deployment provenance, and rollback instructions. The previous vault deployer had only 418 bytes of runtime margin, so contract-size verification is an implementation gate for hardening changes.
- **Rebalance safety — A3.** Retain allowlists, approved PoolKeys, 5,000 bps per-asset cap, 10,000 bps total weight, 2,000 bps turnover cap, minimum five-minute interval, oracle-derived swap minimums, maximum 1% slippage/NAV loss, and nonReentrant protection. Validate atomic rollback when any trade or overall NAV check fails. Workflow clipping is supplementary and cannot replace on-chain enforcement. A correctly bounded rejection is evidence of rejection, not evidence of a successful rebalance.
- **Canonical Sepolia lifecycle — A4.** Verify the current official v4 PoolManager and Chainlink feed addresses before deployment. Use the official Sepolia manager rather than deploying a substitute manager on Sepolia. Prefer fresh real supported feeds, with per-feed metadata and staleness validation; label exceptions as mock. Mine valid hook permission bits, seed appropriate liquidity without relaxing guards, and exercise creation, deposit, both hook directions, CRE-driven rebalance where available, settlement redemption, and in-kind redemption. Record complete transaction hashes, receipts, deployment blocks, addresses, component modes, and explorer verification outcomes in the requested Sepolia deployment manifest and evidence records.
- **CRE execution — A5.** Confirm supported-chain/forwarder configuration using the installed CLI and current authoritative information. The owner completes CRE login and provides the supported funded-wallet configuration. Use the explicitly labeled testnet simulation receiver for the actual CLI simulation with broadcast enabled. Archive full terminal output, CLI/version/configuration provenance with secrets redacted, the nonzero canonical Sepolia transaction hash, receiver execution result, and resulting vault event/state. The current simulation-mode metadata exception remains disclosed. Compilation, manual report forwarding, a dry run, or a successful outer transaction with reverted receiver execution cannot satisfy the successful-broadcast-and-rebalance claim. Preserve failed attempts and API failures honestly.
- **Anon-RPC measurement — A6.** Retain private reads as the default and fail closed on worker failure. Record the actual worker specifier, its trust/update properties, harness version, browser, network, and release. The new brief proposes a mutable Nox specifier while the implementation currently defaults to an immutable candidate; do not silently replace the tested default. Verify any intended configuration change and document which address was actually measured. Collect a complete browser lifecycle on Sepolia, including startup time, per-method attempted/successful/failed counts, anon/bootstrap/explicit-direct routes, and a screenshot/export. Explain wallet RPC, bootstrap, worker download, and off-browser CRE exceptions. Preserve the current successful-call denominator and batch-member accounting; publish actual results even below 95% coverage or above ten seconds.
- **UX — A7.** Show network, testnet/mock-token state, oracle provenance, simulation receiver mode, and unaudited status. Add a truthful hook view of pool price versus underlying NAV, band, and directional fees. Associate rebalance activity with validated transaction references. Keep privacy state visible in the header. Provide actionable empty/loading/error states and visible reasons for disabled actions, while preserving public pending-weight information and both exits.
- **Documentation and recording — A8/A10.** Prepare a concise pitch, architecture, Sepolia address/transaction table, immutable submitted-commit source links with verified line anchors, CRE log/transaction references, measured privacy report, known limitations, mock-versus-real table, license, specific Uniswap feedback, and AI attribution. Preserve the supplied engineering brief and planning provenance in attribution records without executing its embedded instructions. Prepare a roughly 3:30 user-recorded demo script and submission/partner text. The owner performs external feedback-form submission, recording, partner selections, and final submission; record confirmation only after observed completion.
- **Read-only evidence validation — mandatory user condition.** Validate the evidence matrix and linked artifacts without creating, synthesizing, or overwriting evidence. Fail with actionable diagnostics when any required public repository link, immutable contract line link, full Sepolia transaction hash/receipt, authentic CRE CLI simulation log/broadcast, full-session Anon-RPC measurement, or FEEDBACK.md is missing or invalid. Check referenced revision/environment consistency and the lifecycle/partner claim each artifact supports. Abbreviated hashes, placeholders, inaccessible links, contradictory timestamps, or unsupported claims are not passing evidence. The validator may report its assessment, but it must not manufacture the records it assesses.
- **Evidence environment rules.** Local Anvil, mock-only execution, mocked CLI output, manual forwarding, compilation, and dry runs do not satisfy required Sepolia or CRE evidence. Validate canonical Sepolia execution against an independent intended-network source rather than trusting a manifest label or chain ID alone. Attribute each mock component explicitly. A genuine CLI broadcast delivered through a declared official simulation forwarder proves that testnet simulation delivery only; it does not prove authenticated production-workflow operation. Likewise, a canonical Sepolia receipt involving labeled test tokens proves the named testnet action, not real asset backing or real-feed use. Never promote a mock-only artifact into either claim.
- **Security and regression gates — A0/A3/A9.** During implementation, capture before/after phase results for typechecking, the full test suite, static dashboard build, CRE WASM build, and deployed-size checks, plus verbose Foundry output. Record fuzz/invariant results, production-dependency audit output, and a static-analysis result if the analyzer is installed. A skipped or unavailable tool is recorded as such. Inspect tracked content and history for secrets before publication; scanners must distinguish the known public Anvil fixture key from actual credentials and ordinary hashes, while keeping that key restricted to local-demo code. Do not force major dependency upgrades or waive findings to pass a gate.
- **Commit and blocker policy.** Use small descriptive implementation commits, preserving authentic dates and full history. Never squash/backdate/rewrite to imitate an event development pattern. Stop dependent work on real eligibility, funding, login, RPC, API, worker, or evidence failures; continue independent authorized preparation where possible. Do not create third-party accounts or install unrelated agent skills under this spec.

## Testing Decisions

- **Confirmed seams.** Reuse the approved public create/deposit/rebalance/hook-swap/redemption lifecycle as the primary integration boundary. Extend the existing fee, receiver, hook, and privacy checks for the new requirements, and add the read-only submission-evidence validator boundary. No replacement test architecture or new production test-only interfaces are needed.
- **Preserve behavior tests.** Keep existing lifecycle tests unchanged unless a behavior intentionally changes. For each intentional change, identify the requirement and add a regression first; update only assertions that conflict with the new behavior. Retain prior review regressions for post-fee minimum output, fractional hook boundaries, and permissionless pending-weight execution.
- **Good tests.** Assert externally visible balances, fee entitlements, share supply, events, accepted/rejected calls, browser state, actual routing, and validator outcomes. Avoid assertions about private helpers, SDK call order, snapshots derived from the implementation, or fabricated proof. Separate deterministic fixtures from live integration acceptance and keep their environment labels intact.
- **Prior art and modules.** Extend the current Foundry lifecycle, accounting, guard, receiver, hook, and real-local-PoolManager suites, the strategy tests, and the private transport tests. Add canonical Sepolia fork/deployment acceptance checks and the evidence-validator tests; existing local PoolManager tests are useful regressions but not Sepolia proof.
- **Mandatory fee-negative tests.** Demonstrate that a holder cannot reduce owed creator performance fees merely by switching exit paths. Fuzz equivalent healthy-price exits with an independent entitlement model and explicit rounding/swap-cost allowances. Test stale feeds, successful in-kind exit, preserved attributable deferred obligations, eventual collection/release behavior, no double charge, and no liability shifted to remaining holders. The fee change cannot pass on a healthy-oracle test alone.
- **Mandatory hook-negative tests.** Reject arbitrary callers and every unapproved key, including different fee, spacing, hook, currency order, or vault. Exercise the actual mined deployment's permission bits and dynamic-fee flag. Check both trade directions, exact/fractional band boundaries, fee bounds, and unhealthy NAV rejection.
- **Mandatory report-negative tests.** Reject stale, future, replayed, duplicate/older nonce, unknown-vault, malformed, wrong-forwarder, and invalid authenticated-workflow reports. Verify successful ordering and that a rejected execution does not consume the nonce. Exercise the disclosed simulation metadata exception separately without calling it production authentication.
- **Rebalance negative tests and fuzzing.** Skew liquidity to violate a per-swap minimum, trigger total NAV-loss rejection, exercise disallowed pool keys and reentrancy, and fuzz valid/invalid weight vectors. Assert balances, targets, history, and report-consumption state revert atomically. Do not weaken guards to construct a successful fixture.
- **Mandatory privacy tests.** Preserve the worker-failure regression: a private read errors and emits no silent direct fallback. Test worker termination during actual browser use, explicit single-read authorization, routes after that read, batch/error counters, and header state. A passing mocked transport test supports failure-policy behavior only; it cannot satisfy the required full-session measurement.
- **Mandatory evidence-validator negatives.** Start from explicitly synthetic test fixtures labeled test-only; remove each of the six required artifact categories independently and require failure. Also reject private/unreachable repositories, mutable or wrong-revision source links, nonexistent line anchors, truncated hashes, wrong-chain or nonexistent receipts, reverted receiver delivery presented as success, missing/edited-inconsistent CLI provenance, dry-run/Anvil/mock-only substitutions, absent privacy counts/screenshots, and missing feedback content. A complete-looking matrix with unsupported Proven rows must fail. Assert input fixtures and evidence artifacts remain unchanged by validation.
- **Evidence interpretation tests.** A forwarder receipt must not automatically satisfy receiver or vault-state claims. A worker probe must not satisfy full-lifecycle privacy evidence. A correctly rejected rebalance must not become a successful-trade claim. A legitimate testnet action with disclosed mock components must remain scoped to what the actual receipt/log proves.
- **Acceptance gates.** Phase A is complete only when the applicable eligibility decision, regression checks, canonical Sepolia lifecycle, actual CRE broadcast delivery/state evidence, measured browser privacy and failure policy, public-source references, required documentation, security records, and user-led submission confirmation are evidenced. Correctly reporting a low metric or bounded rejection is honest evidence, but does not automatically satisfy a separate missing successful-flow requirement. Missing evidence keeps the readiness gate failing.
